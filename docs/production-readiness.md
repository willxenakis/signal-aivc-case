# Production readiness: first failures, monitoring, and fallback

## What would break first

At 40-60 enquiries per week, infrastructure capacity is unlikely to be the first problem. The first failure would be semantic: real enquiries will be shorter, noisier, more political, and less balanced than the synthetic data, while service-line owners may disagree about where work belongs. That creates taxonomy and labeling drift before it creates a scaling problem. Company identity and enrichment would be another early weakness because the brief does not guarantee a trustworthy domain or CRM account ID. Provider latency, quota, and malformed structured output would affect responsiveness, but they are easier to detect than a plausible-looking wrong route. Finally, browser-local workflow state is intentionally non-production: it cannot support multiple users, durable audit history, or reliable downstream notifications.

## What I would monitor

I would instrument the full funnel rather than report model accuracy alone. Operational measures would include provider success and error category, average and p95 latency, token cost, research coverage and freshness, evidence-validation failure rate, queue depth, and time to human resolution. Decision-quality measures would include service-line distribution, per-line recall, auto-route precision, review capture, unnecessary-review rate, analyst overrides, team-lead returns, and complexity corrections. Every record would carry model, prompt, taxonomy, schema, research, and routing-policy versions so a regression could be isolated and rolled back. I would also compare intake-only and enriched decisions to identify whether company context helps or harms specific slices.

## Fallback when the model is wrong or unavailable

The current live-error path catches provider or structured-output failure, runs the deterministic evidence baseline, marks provenance as `fallback`, adds `ai_provider_error`, and forces junior-analyst review. Invalid evidence references also force review. If credentials are absent, the prototype deliberately operates in baseline mode for demonstration; production should instead fail a deployment health check or require review for every degraded result. I would add explicit provider timeouts, bounded retries, circuit breakers, dead-letter handling, and a last-known-good model and prompt version. If overrides or evidence failures spike for one service line, I would pause automation for that slice while preserving direct routing elsewhere. When an individual route is wrong, the immediate action is to correct the handoff, inspect the complete decision package, search for similar cases, add the failure to the regression set, and communicate the scoped corrective action rather than defend the model with an aggregate accuracy percentage.
